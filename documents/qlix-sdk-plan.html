Package structure
What the user installs
pip install qlix from qlix import QlixSDK sdk = QlixSDK() # loads ~/.qlix/agent.json automatically await sdk.start("ira") # boots Luna with identity attached
Layers inside the package
Layer 1
identity.py
Loads agent.json. Validates DID format, private key length, scope list. Raises clear errors if anything is missing or malformed. Every other layer depends on this.
Layer 2
signer.py
Ed25519 sign and verify. Takes a payload dict, canonicalises it (sorted keys), signs with private key, returns hex signature. Mirrors your backend's canonicalize() logic exactly.
Layer 3
http_client.py
Thin async wrapper over httpx. Knows your backend base URL. Handles retries (3x, exponential backoff), auth headers, and maps HTTP errors to typed SDK exceptions.
Layer 4
jit.py
When a JIT-scoped action is triggered, sends a JIT request and then polls GET /jit/poll/:id every 2 seconds. Blocks until approved, denied, or timed out (120s). Raises PermissionDeniedError on deny.
Layer 5 — core
sdk.py — QlixSDK + qlix.run()
The main class. Holds identity + signer + http + jit. Exposes qlix.run(action_type, payload, execute_fn). This is the only function Luna ever calls. Everything else is internal.
Layer 6 — bundled
luna/ (subfolder)
Luna lives here as a bundled subfolder. Not a separate pip dependency. One change: every BaseTool.run() is wrapped with qlix.run(). Luna itself is otherwise unmodified.
File tree
qlix/ __init__.py ← exports QlixSDK identity.py ← agent.json loader + validator signer.py ← Ed25519 canonicalise + sign http_client.py ← async HTTP to Qlix backend jit.py ← JIT approval polling sdk.py ← QlixSDK class + qlix.run() exceptions.py ← typed errors (JITDenied, DeviceNotVerified…) luna/ ← bundled execution engine orchestrator.py tool_registry.py memory.py engine.py pyproject.toml ← pip packaging README.md

What travels in each payload
POST /actions/start
did: "did:qlix:abc123" action_type: "web.click" payload: { url, selector } timestamp: "2026-05-03T…" signature: "a3f8c2…" ← signs above fields
POST /actions/complete
action_id: "act_xyz" success: true result: { status: 200 } timestamp: "2026-05-03T…" signature: "b9e047…" ← signs above fields
Passport headers on every web request
X-Qlix-DID: did:qlix:abc123 X-Qlix-Signature: <ed25519 of method+url+timestamp> X-Qlix-Scopes: web.read,web.click X-Qlix-Timestamp: 2026-05-03T08:00:00Z
Any website receiving these can call GET /api/v1/passport/:did to verify the agent is real, credentialed, and within its declared scopes.
All SDK → backend endpoints
→
POST /api/actions/start
Called before every tool execution. Sends DID, action type, payload, timestamp, signature. Returns action_id. Backend verifies signature immediately — if invalid, returns 403 and tool is blocked.
→
POST /api/actions/complete
Called after every tool execution. Sends action_id, success/fail, result, signature. Backend debits wallet on success only (your pay-per-success model). Writes final audit log entry.
→
POST /api/jit/request
Called when a JIT-scoped action is about to execute. Sends action type + full payload. Backend stores it and notifies the user (dashboard/mobile). Returns jit_request_id.
→
GET /api/jit/poll/:id
SDK polls this every 2 seconds while blocked. Returns status: pending | approved | denied. On approved, returns a one-time use token. On denied, SDK raises PermissionDeniedError.
How the SDK authenticates itself to the backend
Every request includes
Header: X-Qlix-DID Header: X-Qlix-Timestamp Header: X-Qlix-Signature ← Ed25519(DID + timestamp + body hash)
Backend verifies by
1. look up agent by DID 2. fetch stored public key 3. verify signature 4. check timestamp ≤ 30s old 5. proceed or 403
No API keys. No bearer tokens. The agent's Ed25519 keypair IS the authentication. This is exactly the same pattern as your verifiable credentials — the private key proves identity, the public key (stored in DB at agent creation) verifies it.
What the backend needs to add (not built yet)
Missing
Action log table
Prisma model for storing every action: id, agentId, actionType, payload, signature, success, result, timestamps.
Missing
JIT request table
Stores pending approvals: id, agentId, actionType, payload, status, one-time token, expiry.
Missing
Wallet debit logic
On /actions/complete with success:true — debit the org/user wallet by the action's rate. Already designed in your billing model.
What can go wrong + how we stop it
✕
Replay attack — attacker captures a signed payload and resends it
Stopped by: every payload includes a timestamp. Backend rejects any request where timestamp is older than 30 seconds. An intercepted payload is useless after 30s.
✕
Forged action logs — someone sends fake /actions/start without running a tool
Stopped by: signature includes the full payload hash. Backend verifies signature against stored public key. Without the private key (only in agent.json, never on server) you cannot forge a valid signature.
✕
Scope escalation — agent tries to use a scope it wasn't granted
Stopped by: backend checks action_type against the agent's stored permissionScopes on every /actions/start. Undeclared scope → 403. The scopes are set at creation time and cannot be changed by the SDK.
✕
JIT bypass — agent executes a JIT-scoped action without approval
Stopped by: two layers. SDK checks jit_scopes from agent.json before calling execute_fn. Backend also checks on /actions/start — JIT actions require a valid one-time JIT token in the payload, else 403.
✕
Private key theft — agent.json is stolen from user's machine
Mitigated by: agent credentials can be revoked instantly from the Qlix dashboard. Revoked agents → all /actions/start return 403 immediately. Future: encrypt agent.json at rest with a passphrase.
✕
Man-in-the-middle — intercept SDK ↔ backend traffic
Stopped by: all backend calls are HTTPS only. Even if traffic is intercepted, the attacker sees a signed payload they cannot re-sign (no private key) and cannot replay (30s timestamp window).
✕
Unverified agent — rogue agent with no Qlix identity calls your backend
Stopped by: every request must include X-Qlix-DID. Backend looks up the DID — if not found in DB, instant 403. No DID = no access, no exceptions.
What the SDK must never do
✕
Never log the private key anywhere — not to console, not to files, not to error messages
✕
Never send the private key over the network — only signatures go to the backend, never the key itself
✕
Never skip the pre-log — if /actions/start fails, the tool must not execute
✕
Never cache JIT approvals — each JIT token is single-use and tied to one specific action payload
